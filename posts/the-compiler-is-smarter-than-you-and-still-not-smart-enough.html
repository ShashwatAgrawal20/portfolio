The compiler is smarter than you (and still not smart enough)

Posted on July 22, 2026 · 6 min read · 1,174 words • Discuss on GitHub

Most of your manual micro-opts are cosplay. The optimizer already did the boring version. You just never looked at the assembly.

I used to “optimize” C the way people rearrange furniture: move things around, feel productive, never measure the room. Then I started reading what clang -O2 actually emitted. Half my cleverness was already gone. The other half was making the optimizer’s job harder.

This is not “trust the compiler, never think.” It’s the opposite: the compiler is better than your vibes, and still terrible at the things you refuse to measure.

The claim

Write the clear version first. Turn on optimizations. Read the asm (or profile). Only then fight.

If you skip the middle steps, you are not engineering. You are performing intelligence for an audience of one.

People get mad at this because it attacks identity: “I know low-level, therefore I must win against gcc by hand.” Knowing low-level means you can verify, not that you must reimplement strength reduction in your head every Tuesday.

What “smarter” actually means

Modern C compilers (GCC/Clang with a normal -O2 / -O3) are extremely good at:

  • Algebraic simplification and strength reduction (*2 vs shift, multiply by constant, etc.)
  • Inlining (when it can see the body)
  • Dead code elimination and constant propagation
  • Loop idioms that become memset / memcpy / vectorized loops
  • Common subexpression elimination
  • Register allocation better than your pet graph coloring on a napkin

They are not “smart” like a senior engineer who understands your product. They are smart like a very fast intern who has memorized every legal transform under the as-if rule and will apply them ruthlessly.

That distinction matters. The compiler optimizes the program you wrote under the language rules. It does not optimize the problem you meant.

Examples that kill sacred cows

Open Compiler Explorer. Same flags both sides. I’m not going to paste twenty screenshots; go break your own myths.

1. “I’ll multiply by shifting because it’s faster” 

int twice(int x) { return x * 2; }
int twice_shift(int x) { return x << 1; }

At -O2, you often get the same lea, add, or shl. The “I used a shift” version is not a personality trait. It’s noise.

2. “Manual loops beat library memory ops” 

void clear(char *p, int n) {
    for (int i = 0; i < n; i++)
        p[i] = 0;
}

Compilers routinely recognize this and emit something that smells like memset or a vectorized clear when it’s legal. Your hand-rolled byte loop is not automatically virtuous. Sometimes it’s worse because you blocked a pattern match with “clever” indexing.

3. “inline means it will inline”

inline is a suggestion soaked in linkage history. Without LTO, the compiler can only inline what it can see. Your header-only discipline, your unity builds, your LTO flags - those matter more than the keyword cosplay.

4. “Branchless is always faster”

Branchless code can win. It can also lose. Mispredicted branches are expensive; so is a long dependency chain of cmovs on a hot path that predicted fine. You don’t know until you measure that path on that CPU.

5. The one that hurts: you “optimized” and regressed

Classic failure mode:

  • hoist something into a global or volatile “to be safe”
  • add asm barriers because a blog said so
  • rewrite a clean loop into pointer soup so you feel closer to the metal

Suddenly the compiler cannot prove non-aliasing, cannot vectorize, cannot eliminate temps. You got more “control” and less speed. Congratulations: you won the argument and lost the cycle budget.

Where the compiler is dumb on purpose

This is the half people skip, and it’s why “just trust -O3” is also cope.

It cannot see across the universe

  • Separate TUs without LTO: no inlining, weaker devirtualization-like outcomes for function pointers
  • Shared libraries and PLT boundaries
  • Calls into code you didn’t compile (libc is often fine; your plugin ABI is not free)

It must respect concurrency and I/O

  • Syscalls, atomics, volatile (for MMIO, not for “threading vibes”)
  • Anything that can be observed by another thread or the kernel

If you wanted the compiler to invent a lock-free protocol from a racy program, you wanted a different profession.

It is not a profiler

It optimizes local transforms. It does not know your P99 latency under load, your disk, your NUMA node, or that this function runs once at startup. Hotness is on you.

It believes your types and your UB-free story

If you lie (strict aliasing, out-of-bounds, data races), “smart” becomes “nasal demons” at -O2. That’s not the compiler being evil. That’s you voiding the warranty and being surprised the car is fast.

UB: not magic, a contract you signed

People love to say “the compiler is too aggressive.” Often the program was never defined. 

// Don't do this. Illustrative only.
int f(int *a, long *b) {
    *a = 1;
    *b = 2;
    return *a; // what if a and b alias? language says they don't via effective type rules
}

If you needed that alias, you needed char *, memcpy, or a union with defined rules - not vibes.

Rule: if your optimization requires UB, it is not an optimization. It is a timed bomb that passes tests on -O0.

A workflow that isn’t cargo cult

  1. Correct clear code (yes, really)
  2. -O2 (or your project’s real flags) - match production
  3. Profile (perf, counters, a simple timer on the hot loop - something)
  4. Read asm for the hot function only (godbolt, objdump -d, Compiler Explorer diff)
  5. Change one thing, remeasure
  6. Keep the change only if the number moves in the direction you care about

If you cannot explain the asm delta, you are not allowed to call it an optimization in code review. You can call it a refactor. Different word. Different pride.

Useful flags to know exist (project-dependent):

  • -O2 / -O3 / -Os
  • -flto when you actually want cross-TU reality
  • -fno-strict-aliasing is not a personality; it’s a confession
  • sanitizers (-fsanitize=address,undefined) before you brag about speed

Drive-by “optimized” PRs

If you contribute to OSS (you should), stop sending:

  • “micro-optimized” patches with no benchmark
  • renames of i to idx in the name of performance
  • “I replaced this with intrinsics” without a host CPU story

Maintainers have seen a thousand of these. The ones that land look like:

  • before/after numbers
  • asm or perf note when relevant
  • clear code still clear
  • no UB fanfiction

Boring, measured patches get merged. Clever cosplay gets “thanks, closing.”

Wrapping up

The compiler is smarter than you at local, legal, mechanical transforms.
You are smarter than the compiler at problem choice, data layout, algorithms, concurrency design, and what “fast” means for users.

Act like it:

  • Don’t hand-compete with strength reduction.
  • Do own layout, allocation strategy, batching, syscalls, and profiles.
  • When you fight the optimizer, bring assembly and numbers, not folklore.

If this made you angry, good. Open Compiler Explorer, paste the function you’re proudest of, and check whether -O2 already did your personality for you.

If it already did: delete the clever version. Keep the clear one. Ship.

Homework: take one function you “optimized” last year. Godbolt it at -O0 vs -O2. If the lesson doesn’t sting a little, pick a hotter function.
