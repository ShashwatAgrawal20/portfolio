I publish from GitHub issues and your CMS is theater

Posted on July 23, 2026 · 6 min read · 1,055 words • Discuss on GitHub

If your “blog stack” needs a database, a theme marketplace, and a plugin that updates itself into a security advisory, you didn’t pick tools. You hired a second job.

I publish from GitHub issues.

Not as a bit. Not as a prototype I mean to replace with Ghost “when I have time.” As the actual pipeline that puts HTML on the internet for this site.

People call that weird. I call most CMS setups theater: a lot of stage machinery so you can perform “I have a blog” while the hard part was always just writing something true and putting files on a host.

What publishing actually is

Strip the product pages and you’re left with a boring pipeline:

  1. Edit text somewhere durable
  2. Turn it into HTML (and maybe an index, maybe a feed)
  3. Put the result on a server
  4. Optionally let people comment or complain

That’s it. Everything else is policy, taste, and anxiety.

A CMS is one way to implement those four steps. It is not a law of nature. It is software that grew a UI around fears: non-technical editors, previews, roles, media libraries, SEO score widgets, “engagement.”

If you are a single engineer writing about kernels and C, most of that UI is a costume.

What the CMS is selling

The pitch is always some mix of:

  • “You won’t have to touch HTML”
  • “Drafts and editorial workflow”
  • “Themes”
  • “Plugins for comments, newsletters, SEO, analytics, A/B, AI slop”
  • “Scale”

For a magazine with writers who don’t git, cool. For a personal technical blog?

You already touch HTML. You already live in git. You don’t need three roles and a staging taxonomy. “Scale” means you hope more than twelve people read the post, not that you need sharding.

The CMS also sells legitimacy. Real blogs have dashboards. Real writers have CMS. That social proof is doing more work than the software.

Theater.

What I actually run

I am not going to turn this into a tutorial. The point is the shape.

  • Source of truth: a GitHub issue in the portfolio repo
  • Publish signal: a blog-post label on an open issue
  • Build: CI runs a small Node script, markdown → static HTML, plus an index JSON and an RSS feed
  • Host: GitHub Pages

Edit on the website, on mobile, in the API, wherever issues work. History is git + issue events. “Discuss on GitHub” is not a plugin; it’s the issue thread.

Is it elegant enterprise architecture? No. Does it ship posts when I label an issue? Yes. Does it require me to babysit PHP upgrades on a VPS I forgot existed? Also no.

That last sentence is the product.

What GitHub already was

Before anyone invented your headless CMS of the week, GitHub already gave you:

Need Already there
Auth Your account
Edit UI Issues (and the API)
History Issue timeline + repo git
Webhooks / automation Actions
Comments The issue itself
Mobile Good enough
Access control Repo permissions

A CMS reimplements a worse, blog-shaped subset of that, then sells it back with a prettier empty state.

If your whole audience is people who already have GitHub accounts, “login with GitHub to comment” is not innovation. It’s acknowledging the monopoly and moving on.

Theater checklist

Your stack might be theater if:

  • The README for the blog is longer than your last three posts combined
  • You spent a weekend on theme tokens and have not published since
  • “Content” lives in a SaaS you don’t control, with an export format you’ll meet again in hell
  • Preview is sacred but you never open the raw output
  • You have draft states, editorial calendars, and one author: you
  • The build requires services that can fail while markdown on disk cannot

None of these make you a bad person. They make the tool the hobby, which is fine if you admit it. Call it a side project in DX. Don’t call it necessary infrastructure for 2k words about a touchpad quirk.

When a CMS is not theater

I’m not doing the “nobody should use WordPress” bit. That’s also cosplay.

A CMS earns its keep when:

  • Non-engineers write and publish without a repo
  • You need real editorial workflow (reviewers, embargoes, roles)
  • Compliance, audit trails, or corporate IT already standardized on one
  • You’re running a multi-author publication, not a personal log
  • Marketing needs a media library and scheduled campaigns more than you need git blame

If that’s your world, use the CMS. Use two. Enjoy the plugin ecosystem.

The theater is pretending a personal systems blog has the same requirements as a media company so you can feel professional while avoiding the blank page.

The uncomfortable part

Deleting the CMS does not make you a writer.

GitHub issues will not fix:

  • empty outlines
  • posts that are just rage without a diagram
  • never hitting publish

The CMS was never the bottleneck. Fear of a permanent URL was. A dashboard full of drafts is a very expensive security blanket.

My setup’s only moral advantage is that it removes excuses. There is no theme to fiddle with. There is an issue, a label, and a build. Either the words exist or they don’t.

Wrapping up

Publishing is text → HTML → host.

GitHub issues + CI + static files is a complete CMS for a single engineer who already lives in git. Everything beyond that should justify itself in hours saved for real readers, not in how much it resembles a product demo.

If your blog software needs a status page, a marketplace, and a conference, cool product. It might still be theater for your blog.

Write the post. Put it somewhere durable. Point DNS or Pages at the output. Skip the second job.
