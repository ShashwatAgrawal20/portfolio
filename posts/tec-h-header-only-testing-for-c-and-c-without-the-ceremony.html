tec.h: header-only testing for C (and C++) without the ceremony

Posted on July 22, 2026 · 6 min read · 1,162 words • Discuss on GitHub

Drop one header in. Write a test. Compile. Run. That’s the whole product.

I got tired of unit testing in C feeling like a side quest with its own build system, package manager, and personality. So I wrote tec.h.

The problem

In Python or Rust, testing is boring in a good way. You write the thing, you assert, you run the runner.

In C, the options often look like:

  • Pull in a framework that wants CMake, a vendored copy, and half a day of “why is this not linking”
  • Write your own assert soup in main, forget to call half the tests, ship bugs
  • Use something excellent but heavy for a 200-line library that just needed five checks

I wanted the boring path:

  1. One file in the tree
  2. No “test framework project”
  3. Same mental model in C and C++
  4. Automatic discovery so I can’t forget to register a test

That’s the bar. Not “replace GoogleTest for a monorepo.” Just: get out of the way.

What tec.h is

tec.h is a header-only unit test library for C and C++.

  • Zero setup: #define TEC_IMPLEMENTATION in exactly one translation unit, #include "tec.h" everywhere else that needs it
  • No build magic required: raw gcc / clang is enough
  • Suites + automatic registration: TEC(suite, name) { ... } and you’re on the list
  • Rich assertions: eq/ne, comparisons, strings, null, floats with tolerance, C++ throws
  • Fixtures: suite setup/teardown and per-test setup/teardown
  • XFAIL / skip / filters / fail-fast / colors (including NO_COLOR)
  • MSVC: works; C tests go through as C++ there because MSVC and GNU constructor tricks are not friends

Early project, API can still move. It already runs real tests for me daily. That’s enough honesty.

Minimal example

// my_test.c
#define TEC_IMPLEMENTATION
#include "tec.h"

TEC(arithmetic, test_addition) {
    TEC_ASSERT_EQ(2 + 2, 4);
    TEC_ASSERT_NE(2 + 2, 5);
}

TEC(string_test, test_strings) {
    const char *str = "hello";
    TEC_ASSERT_STR_EQ(str, "hello");
}

TEC_MAIN()
gcc my_test.c -o test_runner && ./test_runner

You get suite grouping, pass/fail marks, assertion counts. There is no step five.

For a multi-file project: put TEC_IMPLEMENTATION + TEC_MAIN() in one test_runner.c, write tests in other .c files that only #include "tec.h", link them together. The sample Makefile in the repo finds tests for you if you want that.

How registration works (the interesting bit)

The part people ask about is: how do tests show up without a central list?

C: constructors

On GCC/Clang, each TEC(suite, name) expands roughly to:

  1. A static function that is the test body
  2. A static void __attribute__((constructor)) function that runs before main
  3. That constructor calls tec_register(...) with suite, name, file, function pointer

So by the time TEC_MAIN()'s main runs, the registry is already full. You never maintain a table by hand. Forget to link a test object file and that test is gone - same as any other unit test setup - but you never forget to append one more line to a giant array.

C++: static objects with constructors

In C++, the same idea uses a small helper type:

struct tec_auto_register {
    tec_auto_register(..., tec_func_t func, bool xfail) {
        tec_register(...);
    }
};

Each test gets a static tec_auto_register instance. Construction order does the registration. Fixtures use the same pattern.

Macros glue the name tokens into unique symbols so two tests don’t collide at link time.

This is old-school C++ “nifty counter / static init” energy applied to tests. Not novel. Very effective.

Failure: longjmp vs exceptions

When an assertion fails, the test has to stop that test without killing the whole process, and ideally still allow cleanup.

Mode Mechanism
C setjmp / longjmp out of the assertion into the runner
C++ with exceptions throw tec_assertion_failure
C++ with -fno-exceptions falls back to longjmp like C

That split matters:

  • C: if you allocate, then assert, then free, a failed assert skips the free unless you structure it. Use TEC_TRY_BLOCK({ ... assertions ... }) so a failure jumps to the end of the block and cleanup after the block still runs.
  • C++: prefer RAII. Destructors run on throw. If you insist on raw new, try/catch, clean up, rethrow so the runner still records a failure.
  • TEC_ASSERT_THROWS(stmt, Type) (C++ with exceptions): assert that code throws the type you expect. Wrong type or no throw = fail.

I did not invent process isolation. A crashing test can still take down the process. This is a unit runner, not a fuzz harness.

Stuff that grew in once the basics worked

Once “register + assert + report” worked, the annoying parts of real projects showed up.

Filters

./test_runner -f math              # substring on suite.test
./test_runner -f '!slow'           # exclude
./test_runner --file -f math_tests # filter by source filename
./test_runner --fail-fast

Positive filters include; ! filters veto. Multiple flags OR for includes, veto always wins. Simple substring matching, not regex. Good enough for “run the suite I’m editing.”

XFAIL and skip

  • TEC_SKIP("reason") - park a test without deleting it
  • TEC_XFAIL(suite, name) { ... } - must fail to count as success. If it starts passing, that’s an unexpected pass (XPASS) and you get yelled at - usually because someone fixed the bug and forgot the XFAIL

Useful for TDD and for tracking known broken behavior without red CI forever.

Fixtures

TEC_SETUP(buffer_tests) { /* once per suite */ }
TEC_TEARDOWN(buffer_tests) { /* once per suite */ }
TEC_TEST_SETUP(buffer_tests) { /* before each test */ }
TEC_TEST_TEARDOWN(buffer_tests) { /* after each test */ }

Suite setup failure skips the suite. Per-test setup failure skips that test. Same constructor/static registration path as tests.

Floats

TEC_ASSERT_EQ on doubles is how you hurt yourself. Use TEC_ASSERT_FLOAT_EQ (default epsilon-ish tolerance) or TEC_ASSERT_NEAR(a, b, tol) when you know the budget.

Timing and output

Per-test / suite / total timing landed because “which test got slow” is a real question. Colors auto-detect TTY; honor NO_COLOR / FORCE_COLOR; --no-color and --ascii when your terminal is from 1995 or you’re piping to a file.

C++ without a second library

Same header. Same TEC() macros. Compile as C++ and you get exceptions (when enabled), TEC_ASSERT_THROWS, and you can use std::vector, smart pointers, etc. in tests without a parallel framework.

There’s a tec_showcase.cpp in the repo that flexes STL + RAII + XFAIL around intentional failures. Point is: one include for both languages, behavior adapts instead of forking the API.

What it’s not

  • Not a mocking framework
  • Not a benchmark harness (timers are for humans, not publication)
  • Not process-isolated
  • Not “stable 1.0 forever” yet - early, still moving
  • Not trying to win a feature war with Catch2 / GoogleTest / Unity

If you need death tests, parameterized combinatorics, and XML for a dashboard, use the big tools. If you need five suites for a C library without reenacting Enterprise Build, tec.h is aimed at you.

Wrapping up

tec.h exists because I wanted tests in C to feel like a default, not a dependency negotiation.

One header. Constructor-based registration. Assertions that stop the test without deleting the runner. C and C++ sharing the same macros. Filters and XFAIL when the project stops being a toy.

If you try it and something’s dumb, open an issue or a PR. If you just needed permission to skip the CMake ceremony for a small library: granted. Drop the header in and write the damn test.
