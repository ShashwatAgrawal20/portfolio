The setup: why the kernel felt impossible

For a long time “kernel contribution” sat in the same mental bucket as “write a compiler” and “touch grass”: theoretically doable, practically not something people like me do on a random Tuesday.

Then I started compiling my own kernels on Arch. First with the stock Arch config (bloated as hell, but it boots). Then with make localmodconfig so the build only kept modules my machine actually needed. Builds that took forever. A laptop that cooked itself in a bag because lid-switch wasn’t wired up in my config. The usual “I live here now” arc.

Once you’re building and booting your own kernel, the source stops looking like an unreachable cathedral. It starts looking like a codebase. A huge one. But still a codebase - with drivers, lists, and bugs that show up on your hardware.

That last part is the cheat code.

What I actually landed

In June 2026 I sent (and got merged) this:

Input: synaptics - enable InterTouch on Dell Inspiron 3521

  • Subsystem: input / drivers/input/mouse/synaptics.c
  • Maintainer path: Dmitry Torokhov’s input tree → mainline
  • Diffstat: 1 file changed, 1 insertion(+)

Yes. One line.

"DLL0597", /* Dell Inspiron 3521 */

Added to smbus_pnp_ids[] under CONFIG_MOUSE_PS2_SYNAPTICS_SMBUS.

That’s not a humble-brag about minimalism. It’s the point. Kernel work is often not inventing a scheduler. It’s noticing that your hardware is one allowlist entry away from working the way the driver already knows how to make it work.

How the bug showed up

The Synaptics touchpad on the Dell Inspiron 3521 (PNP ID DLL0597) advertises InterTouch / SMBus support. The driver has a path for that. But the PNP ID wasn’t on the SMBus passlist, so the driver fell back to PS/2 and helpfully logged a hint along the lines of: try psmouse.synaptics_intertouch=1.

So the capability was there. The code path was there. The machine just wasn’t on the list of devices allowed to use it automatically.

Hardware I verified against:

  • Dell Inc. Inspiron 3521 (board 06RYX8, BIOS A07)
  • Synaptics fw 8.1 / board id 2382
  • firmware_id "PNP: DLL0597 PNP0f13"

Classic “works if you know the magic module parameter, broken for everyone else” situation. Perfect first-patch material.

The patch itself

The change is intentionally boring:

 #ifdef CONFIG_MOUSE_PS2_SYNAPTICS_SMBUS
 static const char * const smbus_pnp_ids[] = {
 /* all of the topbuttonpad_pnp_ids are valid, we just add some extras */
+"DLL0597", /* Dell Inspiron 3521 */
 "DLL060d", /* Dell Precision M3800 */
 "LEN0048", /* X1 Carbon 3 */
 "LEN0046", /* X250 */

What matters more than the diff:

  1. Reproduced on real hardware - not a theoretical reading of the source.
  2. Matched existing patterns - the file is full of PNP ID entries with model comments. Don’t invent a new style; join the list.
  3. Commit message explains why - what the device advertises, what the driver did without the entry, what the one-line fix does, and the hardware I tested on.
  4. Went through the right maintainer - input subsystem, not a random blast to linux-kernel@.

Commit message shape (roughly what landed):

Input: synaptics - enable InterTouch on Dell Inspiron 3521

The Synaptics touchpad on Dell Inspiron 3521 (PNP ID DLL0597) advertises
InterTouch / SMBus support, but is not on the SMBus passlist, so the
driver falls back to PS/2 and logs a hint to try
psmouse.synaptics_intertouch=1.

Add DLL0597 to smbus_pnp_ids so InterTouch is enabled automatically on
this model (and other Dells that reuse the same PNP ID).

Hardware: Dell Inc. Inspiron 3521 (board 06RYX8, BIOS A07),
Synaptics fw 8.1 / board id 2382, firmware_id "PNP: DLL0597 PNP0f13".

Signed-off-by: Shashwat Agrawal <you@example.com>

Signed-off-by is not decoration. It’s the Developer’s Certificate of Origin. You need it.

How the hell do you get started

Forget “I need to understand the whole kernel.” You don’t. Nobody does.

0. Prerequisites that actually matter

  • Comfortable with C (you don’t need to be a language lawyer; you need to read driver code without crying).
  • A Linux machine you can break a little (or a VM, but hardware bugs need hardware).
  • Git, email setup for git send-email (or the modern b4 workflow).
  • Patience for builds. First full build hurts. Incremental builds after that are fine. ccache helps. More cores help more.

1. Get the source the kernel way

Don’t treat GitHub as the source of truth for sending patches. Use kernel.org trees and the mailing-list workflow. 

# shallow clone is fine to start; deepen later if you need history
git clone --depth=1 https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git
cd linux

For subsystem work you’ll eventually want the maintainer’s tree (for input, that’s Dmitry’s tree) so you’re not posting against a stale base. For a first drive-by fix against mainline, starting from Linus’s tree is okay if you rebase carefully.

2. Build something that boots

On a machine you use daily:

# start from your running config
cp /boot/config-$(uname -r) .config
make olddefconfig

# or shrink to what you actually load:
make localmodconfig

make -j"$(nproc)"
# install + reboot path depends on distro; on Arch people often use
# a custom pkg or just install modules + the image carefully

If you can boot it, you can test it. If you can test it, you can fix it.

3. Learn the social layer before the code layer

Kernel process is half code, half culture:

  • Submitting patches
  • Coding style (yes, tabs)
  • scripts/checkpatch.pl on every patch, every time
  • scripts/get_maintainer.pl so you mail people, not the void 
scripts/checkpatch.pl --strict your.patch
scripts/get_maintainer.pl your.patch

If checkpatch yells, fix it before a human has to.

Finding something to fix

You do not start by emailing “hi I want to contribute, assign me a task.”

Good first patches look like:

Kind Why it works
Hardware quirk / allowlist entry You have the device; maintainers often don’t
Obvious bug you hit Logs, oopses, wrong fallbacks
Docs / comment fixes that fix real confusion Small, but only if accurate
Staging cleanups More review bandwidth, still real

Bad first patches look like:

  • Random drive-by refactors with no bug
  • “Modernize this whole file” style churn
  • Drive-by churn that fights the subsystem’s taste

My path was the first row: hardware I own + driver that already almost supported it.

Practical ways to find that:

  1. Read dmesg on your laptop. Drivers leave breadcrumbs (please try module_param=1, “unknown id”, fallback messages).
  2. Search the driver for allowlists / quirk tables near your PNP/USB/DMI IDs.
  3. Browse Kernel Bugzilla for hardware you have.
  4. Watch the subsystem list for regressions you can reproduce.
  5. Build with extra warnings on code you care about - sometimes the low-hanging fruit falls out.

When you find a candidate, prove it:

  • Before behavior (logs, photos, libinput list-devices, whatever applies)
  • After behavior on a kernel with your patch
  • Enough hardware detail that someone without your laptop can still reason about it

Sending the patch (the scary part)

High-level flow that worked for me:

  1. Topic branch off a recent base.
  2. One logical change per commit. My entire fix was one commit. Good.
  3. Commit message in kernel style: subsystem prefix, imperative subject, body that explains problem → approach → testing.
  4. checkpatch clean.
  5. Find maintainers with get_maintainer.pl.
  6. Send with git send-email (or prepare with b4 / git format-patch and send properly).
  7. Reply to review. Don’t vanish. Don’t take style nits personally.

Minimal git send-email shape:

git format-patch -1 -o outgoing/
scripts/checkpatch.pl --strict outgoing/*.patch
scripts/get_maintainer.pl outgoing/*.patch
git send-email --to="maintainer@…" --cc="list@vger.kernel.org" outgoing/0001-*.patch

For input, that meant the input maintainer and the linux-input list - not “email Linus.”

After it was accepted into the input tree, it rode the normal path into mainline. Seeing your name on torvalds/linux hits different than a GitHub PR merge button. Same dopamine class. Different weight.

What surprised me

Small is fine. Maintainers would rather merge a correct one-line quirk than debate a 400-line “cleanup.”

Process is the real gate. Style, SoB, correct lists, correct base, correct people. The C is often the easy half.

Your hardware is an unfair advantage. Big vendors and big subsystems still miss specific SKUs. If you own the weird laptop, you can be the person who makes Linux better on that laptop for everyone after you.

Review is not hostility. Short, blunt review is normal. Fix the thing, resend, move on.

Building the kernel teaches more than reading blogs about the kernel. Config pain, module deps, “why won’t suspend work,” reading dmesg like a stack trace - that’s the real onboarding.

Resources that actually helped

  • Kernel Newbies - orientation, not cargo cult
  • LF docs: submitting patches
  • LFD103 - beginner path if you want structure
  • Subsystem MAINTAINERS file + get_maintainer.pl - non-negotiable
  • checkpatch.pl - your first reviewer, free and unemotional
  • lore.kernel.org archives for the subsystem you care about - read how people talk before you post

And unglamorous but real: just compile the damn thing until boot works. Everything after that is incremental.

Wrapping up

My first kernel contribution was not a new subsystem. It was a PNP ID string for a Dell touchpad so InterTouch could turn on without a module parameter.

If you’re waiting until you “know enough kernel” to start: you will wait forever. Pick a machine you own. Read what its drivers print. Find the allowlist, the quirk, the off-by-one, the missing static, the doc that lies. Make the smallest correct change. Run checkpatch. Mail the right people. Iterate.

One line is enough to get in the door.

After that, you already know the path - you just take it again on a harder bug.
